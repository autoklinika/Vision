# ECU reference profile V1 implementation

The reference profile is an offline declarative snapshot. `load_json` validates the closed 15-section V1 schema and returns a deeply immutable `ReferenceProfile`; `canonical_json` returns deterministic JSON and `content_sha256` computes the domain-separated content digest. See the accepted V1 specification and template for complete field shapes. The template is a DRAFT preview and is never executable.

Register explicit profiles with `ReferenceLibrary.register(profile)` and select by the exact `(family_id, variant_id, profile_revision)` using `select`. `list_profiles` and `preview` expose immutable metadata, states and workflows, including DRAFT entries. Registration snapshots canonical JSON and checks for changes on selection; no discovery or variant substitution occurs.

An APPROVED profile needs a matching `metadata.content_sha256`, `provenance_release.released_snapshot_sha256`, and `release_approval.content_sha256`, as well as approval and verified readiness entries for the exact state, recipe and scope. Publish it with `ReferenceReleaseStore(directory).publish(profile)`. Releases are immutable canonical files in a separate reference namespace, keyed by profile ID and revision; keep the directory controlled and back it up. These hashes correlate snapshots and approvals; they do not authenticate a reviewer or protect against a party controlling the store.

`AssetStore(directory)` opens an existing controlled local directory. Asset records contain `asset_id`, `kind`, `relative_path`, `sha256`, integer `bytes`, `mime`, `physical_state_id`, `source_id`, `verified`, and `privacy_class`. Paths are relative and may contain multiple directory segments. Supported kinds and MIME pairs are defined in `assets.MIMES`. Verification reads at most 128 MiB, checks size and SHA-256, and does not decode images. Place private assets in the controlled directory independently; the store does not download, write, or discover them.

Call `compile_profile(profile, state_id, recipe_id, record, catalog, ecu_release_store, calibrations, capabilities=..., asset_store=..., reference_release_store=..., library=...)`. All stores, calibration revisions and available capabilities are explicit. The ECU record must be independently approved, registered and released. Its profile ID, family, variant and revision must exactly match the reference; the selected envelope, required view poses and selected PCB ROIs must match or fit the approved record. Execution compilation supports photo inspection only; readiness for identity, localization, and thermal scopes does not imply a capture-ready Core profile. The selected required views must exactly match the approved record views, and the returned Core profile contains only selected verified ROI rectangles. The reference release, required assets and scope readiness are checked before a frozen `ExecutionBundle` is returned. `prepare_execution` is an alias. The bundle contains the Core profile, record and reference digests, verified assets, selected state and recipe, required capabilities, module specifications, optional scenario and QA policy references.

When a workflow requires modules, supply an explicit `ModuleRegistry` and `ScenarioSpec` matching its `scenario_ref` and required module IDs. The scenario must retain the Core S01–S11 chain and checks; every module stage must follow localization and be an ancestor of S11. With no modules, omit both and the existing Core workflow uses its default chain. This preparation does not execute a workflow, move hardware, verify a live ECU identity, or mutate a session. Runtime observation, freshness, scene and motion safety gates remain the responsibility of the existing Core workflow. The included test fixtures and byte assets are synthetic and test-only.

Photo-inspection readiness requires a nonempty pinned asset_manifest_revision and verifies quality policies at all three levels: photography section, selected photo recipe and selected views, in addition to the workflow policy requirements. The ExecutionBundle exposes the merged verified QA policy references. A manifest revision is metadata pinned by the snapshot; it is not proof of an authenticated camera source or a physical asset catalog by itself.
